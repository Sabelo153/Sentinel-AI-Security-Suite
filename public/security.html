Security at Sentinel

Operational data deserves disciplined protection.

Sentinel’s application architecture treats identity, company scope and authorisation as separate checks on every protected operation.

Application safeguards

Protection built into the request path.

The controls below describe the current application design. Hosting, backup and monitoring controls depend on the environment chosen for production deployment.

Explicit tenant isolation

Protected records are scoped by company. The runtime tenant context is authoritative, and repository queries use explicit company predicates.

Role-based authorisation

Protected requests pass authentication, tenant resolution and permission checks before business handlers run.

Auditable mutations

High-value operational changes write audit events so authorised reviewers can trace who changed what and when.

Safe data access

Database interactions use prepared statements and controlled validation. API responses use defined error states without exposing internal details.

Encrypted mobile storage

The Android guard workspace protects locally stored operational data and supports controlled synchronisation after offline work.

Operational resilience

Deployment guidance covers backups, restoration, monitoring and provider configuration so production operators can complete the infrastructure layer.

Shared responsibility

Secure software still needs secure operation.

Sentinel provides application controls, but each organisation remains responsible for assigning access carefully, protecting account credentials, reviewing personnel changes and configuring its production environment.

Before production use, the deployment owner should complete infrastructure hardening, encrypted transport, backup and restore testing, monitoring, notification-provider setup and incident response contacts.

Security reporting: A dedicated public vulnerability-reporting address and disclosure process must be added when the final operating entity and production domain are confirmed.
